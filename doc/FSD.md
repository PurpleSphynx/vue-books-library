# Архитектура проекта

## Принципы

Проект использует **Feature-Sliced Design (FSD)** — архитектурный подход, основанный на принципе **методичного разбиения по слоям**. Каждый слой имеет свою зону ответственности, а зависимости движутся **сверху вниз**.

### Dependency direction

```
app → pages → widgets → features → entities → shared
```

Каждый слой может импортировать только слои **ниже** себя. Импорт «вверх» запрещён.
При этом слой не обязан использовать каждый слой, расположенный ниже. Например, `pages` может напрямую использовать `features`, `entities` и `shared`, а `entities` — только `shared`.

Допустимые направления:

app     → pages, widgets, features, entities, shared
pages   → widgets, features, entities, shared
widgets → features, entities, shared
features → entities, shared
entities → shared
shared  → shared

Недопустимые направления:

entities → features
entities → widgets
entities → pages
entities → app

features → widgets
features → pages
features → app

shared → entities
shared → features
shared → widgets
shared → pages
shared → app
---

## Слои

### `app/`

**Что это:** Application-level конфигурация и инфраструктура.

**Содержимое:**
- `App.vue` — корневой компонент
- `main.ts` — точка входа
- `router/` — маршрутизация
- `styles/` — глобальные стили
- `model/` — application-level state (auth store)
- `api/` — application-level API (auth)
- `lib/` — инфраструктурные утилиты (token guard)

**Правило:** `app/` содержит код, который apply ко всему приложению и не привязан к конкретной domain entity.

---

### `pages/`

**Что это:** Route-level компоненты. Каждая страница = один маршрут.

**Содержимое:** Vue-компоненты, которые:
- Собирают entities/widgets/shared UI в готовый экран
- Управляют UI orchestration (какие composables вызывать, когда обновлять данные)
- Содержат минимальную business logic (только ту, которая специфична для этой страницы)

**Правило:** Page не должна содержать API-вызовы напрямую — только через composables/entities. Page не должна импортировать другие pages.

---

### `widgets/`

**Что это:** Крупные reusable UI-блоки, которые собирают несколько entities/features.

**Содержимое:** Компоненты, которые:
- Используют несколько entities или features одновременно
- Представляют собой законченый UI-блок (навигация, форма, панель)

**Правило:** Widget не должен содержать бизнес-логику — только UI orchestration.

---

### `features/`

**Что это:** Пользовательские действия и законченные сценарии, имеющие самостоятельную бизнес-ценность.

Feature отвечает на вопрос **«что пользователь делает?»**, тогда как entity отвечает на вопрос **«с чем пользователь работает?»**.

**Примеры:**
- авторизация пользователя
- создание сущности
- редактирование сущности
- удаление сущности
- добавление товара в корзину
- оформление заказа
- отправка комментария
- фильтрация каталога
- экспорт данных
- изменение настроек пользователя

**Содержимое:**
- `ui/` — UI конкретного пользовательского сценария
- `model/` — состояние и логика сценария
- `api/` — feature-specific API, если запрос относится именно к действию, а не к самой entity
- `lib/` — вспомогательная логика feature, если она не имеет смысла вне этого сценария

**Критерий feature:**

Feature имеет смысл выделять, если выполняется хотя бы одно из условий:

- представляет самостоятельное пользовательское действие;
- содержит бизнес-логику конкретного сценария;
- объединяет несколько entities для выполнения одного действия;
- имеет собственное состояние, валидацию или orchestration;
- один и тот же пользовательский сценарий используется в нескольких местах.

**Пример:**

entities/product/
    model/
    api/
    ui/

features/add-to-cart/
    model/
    ui/

#### **Правила**

- Feature должна представлять самостоятельное пользовательское действие или законченный пользовательский сценарий.
- Feature должна отвечать на вопрос **«что пользователь делает?»**, а entity — **«с чем пользователь работает?»**.
- Feature может содержать собственные `api/`, `model/`, `ui/` и `lib/`, если они непосредственно относятся к этому сценарию.
- Feature может использовать `entities` и `shared`, но не должна зависеть от `widgets`, `pages` или `app`.
- Feature может использовать несколько entities, если они участвуют в одном пользовательском сценарии.
- Feature может содержать state, validation, orchestration и business logic, необходимые для реализации конкретного сценария.
- API feature должно содержать запросы, относящиеся непосредственно к пользовательскому сценарию, а не к generic HTTP infrastructure или отдельной entity.
- Если API-операция представляет самостоятельную операцию над entity и не зависит от user flow, её следует рассмотреть для размещения в `entities`.
- UI feature должен представлять действие или сценарий пользователя, а не просто отображать entity.
- Feature не должна знать, на какой конкретной странице или внутри какого widget она используется.
- Feature может использовать entity UI, model и API, но entity не должна зависеть от feature.
- Feature не должна содержать generic-код, который не знает о предметной области. Такой код следует размещать в `shared`.
- Сторонняя библиотека не определяет слой автоматически. Интеграция со сторонней библиотекой должна находиться в `shared`, `entities`, `features` или `app` в зависимости от её ответственности.
- Если сторонняя библиотека используется для реализации конкретного пользовательского сценария, её integration code может находиться внутри соответствующей feature.
- Navigation, являющаяся частью пользовательского сценария, может находиться в feature.
- Feature не должна становиться контейнером для всей логики страницы. Screen-level orchestration относится к `pages`, а крупная UI composition — к `widgets`.
- Не каждое действие пользователя должно становиться отдельной feature. Простое локальное действие без самостоятельной бизнес-ценности может оставаться внутри компонента или страницы.
- Feature следует выделять, если сценарий имеет самостоятельную бизнес-ценность, собственную логику, состояние, validation, API или используется в нескольких местах.
- Несколько entities, объединённых одним пользовательским сценарием, являются хорошим кандидатом для feature.
- Если feature начинает использовать другую feature, следует проверить, действительно ли обе являются самостоятельными сценариями или их общую часть нужно вынести ниже.
- Feature не должна зависеть от конкретной реализации page или widget.
- Feature должна быть максимально независимой от конкретного экрана и пригодной для использования в нескольких местах, если сам сценарий это допускает.


### `entities/`

**Что это:** Самостоятельные объекты предметной области, имеющие собственные данные, правила и идентичность.

Entity отвечает на вопрос **«с чем работает приложение?»**.

**Примеры:**
- User
- Product
- Order
- Book
- Author
- Article
- Payment
- Project

**Содержимое:**
- `api/` — запросы и операции, непосредственно относящиеся к entity
- `model/` — domain types, state и логика, непосредственно относящиеся к entity
- `ui/` — представление entity, если оно необходимо
- `lib/` — вспомогательная логика entity, если она не является самостоятельным пользовательским сценарием

**Критерий entity:**

Entity имеет собственную предметную сущность, которая:
- имеет собственный domain type;
- имеет собственные данные;
- обладает идентичностью или устойчивым понятием в предметной области;
- может иметь собственные операции, правила или API;
- используется в одном или нескольких пользовательских сценариях.

**Пример:**

entities/
└── product/
    ├── api/
    ├── model/
    ├── ui/
    └── lib/

Entity product может содержать тип Product, операции получения и изменения продукта, а также компоненты или функции, которые непосредственно представляют продукт.

#### **Правила**

- Entity должна представлять самостоятельное понятие предметной области, а не конкретный пользовательский сценарий.
- Entity может содержать собственные `api/`, `model/`, `ui/` и `lib/`, если они непосредственно относятся к этой entity.
- API entity должно содержать операции, непосредственно связанные с этой entity.
- Общий HTTP client, transport, interceptors и другие domain-agnostic механизмы должны находиться в `shared` или `app`, а не внутри entity.
- Entity может содержать state и domain logic, непосредственно относящиеся к этой entity.
- UI entity может представлять саму entity, но не должен реализовывать самостоятельный пользовательский сценарий.
- Если логика описывает действие пользователя над entity (`create`, `edit`, `delete`, `add-to-cart`, `checkout` и т. п.), следует рассмотреть размещение этой логики в `features`.
- Entity не должна зависеть от `features`, `widgets`, `pages` или других верхних слоёв.
- Entity не должна знать, на какой странице или в каком пользовательском сценарии она используется.
- Entity может использовать только `shared` и другие части того же entity.
- Сторонняя библиотека не определяет слой автоматически. Слой определяется ответственностью интеграции.
- Generic-интеграция со сторонней библиотекой должна находиться в `shared`, если она не знает о предметной области.
- Domain-specific интеграция со сторонней библиотекой должна находиться внутри соответствующей entity или feature.
- Application-level интеграция со сторонней библиотекой должна находиться в `app`.
- Например, generic wrapper над chart library может находиться в `shared/lib/chart`, а `SalesChart`, который знает о `Order`, `Revenue` и других domain concepts, не является generic и должен находиться выше.
- Navigation, которая является частью конкретного пользовательского сценария, относится к соответствующей `feature`.
- Generic navigation helpers могут находиться в `shared`.
- Router и его application-level configuration относятся к `app`.
- Domain-specific URL builders и navigation helpers должны находиться в соответствующей entity или feature, если они знают о конкретном domain или user flow.
- Переиспользование само по себе не делает entity частью `shared`. `ProductCard`, например, может использоваться во многих местах и при этом оставаться `entities/product/ui`.
- Entity должна быть максимально независимой от конкретного пользовательского сценария.
- Если код начинает зависеть от конкретного user flow, page или widget, следует проверить, не является ли он `feature` или кодом более высокого слоя.

---

### `shared/`

**Что это:** Domain-agnostic инфраструктура и generic UI.

**Содержимое:**
- `api/` — generic HTTP client
- `types/` — общие типы (ApiError, Pagination, ListResponse)
- `ui/` — generic UI-компоненты (кнопки, инпуты, модалки)

**Правило:** Shared содержит **только** код, который может существовать в другом проекте без знания о предметной области текущего приложения. Если код знает о Book/Author/Report — он не должен находиться в shared.

## Dependency direction — детально

```
app/router       → app/lib/token-guard
app/model        → app/api/auth-api → shared/api/httpClient
app/model        → app/lib/token-guard

pages/*          → entities/book/model/*
pages/*          → entities/author/model/*
pages/*          → shared/ui/*
pages/*          → app/model/auth-store

entities/book/api    → shared/api/httpClient
entities/author/api  → shared/api/httpClient

shared/api/httpClient → shared/types
shared/ui/*           → shared/types
```

**Нет циклических зависимостей. Shared не зависит от entities. Entities не зависит от pages.**

## Почему именно так

FSD нужен не ради определённой структуры папок. Его основная цель — **управлять зависимостями, разделять ответственности и ограничивать связанность кода**.

По мере роста приложения код начинает связываться сразу по нескольким направлениям:

- UI зависит от бизнес-логики;
- бизнес-логика зависит от API и инфраструктуры;
- страницы используют несколько частей приложения;
- разные пользовательские сценарии используют одни и те же entities;
- сторонние библиотеки начинают проникать в domain code;
- generic utilities начинают получать знания о предметной области;
- изменения в одном месте требуют изменений во многих других местах.

FSD вводит архитектурные границы, которые делают эти зависимости явными.

### Почему есть несколько слоёв

Каждый слой отвечает на свой вопрос:

- `app` → как работает всё приложение?
- `pages` → какие экраны существуют?
- `widgets` → из каких крупных блоков состоят экраны?
- `features` → что пользователь делает?
- `entities` → с какими объектами работает приложение?
- `shared` → что не знает о предметной области?

Это позволяет определять место нового кода по его ответственности, а не по тому, куда удобнее положить файл.


### Почему зависимости идут только вниз

Более высокий слой содержит больше application-specific контекста.
Например, `Product` не должен знать, что существует `AddToCart` или `ProductPage`.
Иначе domain code начинает зависеть от конкретного пользовательского сценария или экрана и теряет независимость.
Поэтому зависимости направлены от более специализированного контекста к более общему:
`app → pages → widgets → features → entities → shared`
Чем ниже слой, тем меньше application-specific context он должен знать.


### Почему `shared` находится внизу

`shared` предназначен для кода, который не знает о предметной области приложения.

Например:
- generic HTTP client;
- базовые UI-компоненты;
- форматирование;
- generic utilities;
- интеграции со сторонними библиотеками, не знающие о domain.

Такой код потенциально можно использовать в другом приложении.
Если `shared` начинает импортировать `Product`, `Order`, `User`, `Checkout` и другие domain concepts, это сигнал, что код перестал быть generic и, вероятно, находится не на том слое.
Главный принцип:
> Если код в `shared` знает о конкретной предметной области, он, скорее всего, не должен находиться в `shared`.


### Почему `entities` нужны отдельно

Entity представляет самостоятельное понятие предметной области.
Например:
- `User`;
- `Product`;
- `Order`;
- `Payment`.
Entity отвечает на вопрос:
> **С каким объектом предметной области работает приложение?**
Entity не обязана иметь CRUD, отдельную страницу или сложный UI.
Она может быть read-only, использоваться несколькими сценариями или существовать только как часть другого пользовательского процесса.
Критерием является наличие самостоятельного domain concept, а не количество endpoints или файлов.


### Почему нужны `features`

Без features пользовательские сценарии начинают расползаться по pages и entities.
Например, сценарий «проверить товар → проверить доступность → добавить в корзину → обновить состояние → показать уведомление» не является свойством `Product`.
Это самостоятельное пользовательское действие.
Поэтому FSD разделяет:
- `Entity` → с чем работает пользователь;
- `Feature` → что пользователь делает.
Features позволяют не помещать сценарную логику внутрь entity только потому, что сценарий работает с этой entity.


### Почему feature может использовать несколько entities
Реальный пользовательский сценарий часто затрагивает несколько domain objects.
Например, `checkout` может использовать:
- `Cart`;
- `Product`;
- `Order`;
- `Payment`.
Это нормально.
Feature является уровнем, который связывает несколько entities в рамках одного пользовательского действия.
При этом сами entities не должны знать о checkout.


### Почему не каждое действие пользователя становится feature
FSD не означает «каждая кнопка = feature».
Например:
- `toggleMenu`;
- `setActiveTab`;
- `openModal`;
могут быть обычной локальной логикой компонента.
Feature имеет смысл, когда действие обладает самостоятельной бизнес-ценностью, содержит заметную логику или является отдельным пользовательским сценарием.
Иначе появление множества микроскопических features только усложнит проект.

### Почему `widgets` существуют отдельно от `features`
Feature и widget решают разные задачи.
- `Feature` → пользовательское действие;
- `Widget` → крупный UI-блок.
Например, `add-to-cart` описывает возможность добавить товар в корзину.
А `product-summary` может собрать:
- информацию о товаре;
- цену;
- доступность;
- `AddToCart`;
- отзывы.
Widget отвечает за композицию интерфейса и может использовать несколько entities и features.


### Почему `pages` должны быть относительно тонкими

Page представляет конкретный экран или маршрут.
Её основная задача — собрать необходимые части приложения и определить их расположение на экране.
Если page начинает содержать большое количество domain logic или user-flow logic, это повод проверить, не должна ли эта логика находиться в entity или feature.
При этом page может содержать:
- screen-level orchestration;
- route-specific logic;
- связывание нескольких частей приложения;
- логику, которая имеет смысл только на конкретном экране.


### Почему API не находится в одном глобальном месте
API следует разделять по ответственности.
`shared/api` может содержать generic HTTP infrastructure:
- HTTP client;
- request helpers;
- interceptors;
- serialization.

`entities/product/api` может содержать операции непосредственно над Product:
- получение Product;
- получение списка Product;
- изменение Product.

`features/checkout/api` может содержать API, относящееся именно к checkout scenario.

`app/api` может содержать application-level API, если оно относится ко всему приложению.

Главное правило:
> Не следует собирать все HTTP-запросы в один глобальный `api/` только потому, что технически все они используют HTTP.


### Почему сторонние библиотеки не образуют отдельный слой

FSD классифицирует код по ответственности, а не по происхождению.
Сторонняя библиотека может использоваться на разных уровнях:
- chart library;
- date library;
- validation library;
- storage library;
- HTTP library.

Важно определить границу интеграции.
Generic integration относится к `shared`.
Domain-specific integration относится к соответствующей `entity`.
User-flow-specific integration относится к соответствующей `feature`.
Application-specific integration относится к `app`.
Таким образом, сама библиотека не определяет слой.
Определяет слой **контекст, который знает integration code**.


### Почему `shared/lib` не должен становиться папкой для любых `utils`
Название `utils` ничего не говорит об архитектурной ответственности.
Например, `formatDate`, `debounce` и `deepEqual` могут быть generic.
Но `calculateOrderDiscount`, `getBookAvailability` и `buildCheckoutPayload` знают о предметной области и не становятся `shared` только потому, что являются функциями.
Поэтому:
> `shared` определяется отсутствием domain context, а не простотой, размером или количеством использований кода.


### Почему переиспользование само по себе не определяет слой
Распространённая ошибка:
> «Этот компонент используется во многих местах, значит он должен быть в `shared`».
Это не обязательно.
Например, `ProductCard` может использоваться на десяти страницах и всё равно оставаться entity-level UI, потому что он знает о Product.
Главный вопрос:
> Знает ли код о конкретной предметной области?
Если знает — он не является generic shared code.


### Почему UI разделён между слоями
Разные UI-компоненты имеют разную ответственность:
- `shared/ui` → generic UI;
- `entities/*/ui` → domain UI;
- `features/*/ui` → UI пользовательского сценария;
- `widgets/*` → крупная UI composition;
- `pages/*` → экран.

Местоположение компонента уже сообщает его архитектурную роль.


### Почему не нужно заранее создавать все слои
FSD не требует, чтобы каждый проект обязательно имел все возможные слои.
Если конкретный слой не нужен, его можно не создавать.
Небольшое приложение может начать с `app`, `pages` и `shared`.
По мере появления соответствующей сложности могут появиться `entities`, `features` и `widgets`.
FSD предназначен для управления сложностью, а не для искусственного создания структуры.


### Как определить слой для нового кода

При добавлении нового модуля полезно последовательно задать вопросы:
1. Относится ко всему приложению? → `app`
2. Представляет экран или маршрут? → `pages`
3. Представляет крупный UI-блок? → `widgets`
4. Представляет самостоятельное пользовательское действие? → `features`
5. Представляет объект предметной области? → `entities`
6. Не знает о предметной области? → `shared`

Если подходят несколько вариантов, следует выбрать слой по **основной ответственности кода**.


### Как понять, что код находится не на своём слое

Хорошими архитектурными сигналами являются:
- `Page` содержит много domain logic;
- `Entity` начинает знать о конкретном user flow;
- `Feature` начинает зависеть от конкретной page;
- `Widget` превращается в самостоятельный business workflow;
- `Shared` начинает импортировать domain code;
- `Shared utility` начинает знать о Product, Order, User и других domain concepts.
Это не означает, что код обязательно нужно немедленно переносить.
Это сигнал для пересмотра ответственности модуля.


### Главный принцип FSD

Все правила можно свести к одному:
> **Код должен находиться на самом нижнем слое, который обладает достаточным контекстом для его реализации, но не зависит от более высокого контекста.**
Например:
- `formatDate` → `shared`;
- `Product` → `entities`;
- `AddToCart` → `features`;
- `ProductSummary` → `widgets`;
- `ProductPage` → `pages`;
- router configuration → `app`.
Чем ниже код находится в архитектуре, тем более независимым и generic он должен быть.
Чем выше он находится, тем больше application-specific context он может содержать.


### Главная идея FSD

FSD — это не столько набор обязательных папок, сколько **система управления ответственностями и направлениями зависимостей**.
Структура `app → pages → widgets → features → entities → shared` нужна для того, чтобы:

- ограничивать связанность кода;
- отделять domain objects от пользовательских сценариев;
- не допускать проникновения application-specific logic в нижние слои;
- изолировать инфраструктуру и сторонние библиотеки;
- делать зависимости предсказуемыми;
- упрощать поиск места для нового кода;
- уменьшать стоимость изменений по мере роста приложения.
Главная ценность FSD не в структуре папок, а в том, что **архитектурные границы становятся явными и проверяемыми**.
